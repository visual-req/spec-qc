## よくある質問とトラブルシューティング

### 1) スキャンが途中で失敗した場合の原因の特定方法

まずはログを確認してください：

- `work/logs/spec-qc.log`：スキャンプロセス全体（どのファイルのどのルールセグメントで失敗したか、例外スタックトレースを記録します）。
- `work/logs/large-model.log`：モデルリクエストとレスポンスのサマリー（デフォルトでは機密内容は記録されません）。

### 2) Model output is not valid JSON

原因：モデルのレスポンスが途切れたか、指定通りにJSONを出力しませんでした。

現在の戦略：

- プロンプトで出力サイズ（問題数とフィールドの長さ）を制限しています。
- パーサーは途切れたJSONの修復（不足している括弧の追加/途切れた末尾のロールバック）をベストエフォートで試みます。

それでも頻繁に発生する場合：

- 1回のリクエストあたりのルール数を減らします（ルールファイルのサイズを小さくするか、ルールファイルを分割します）。
- ネットワーク/プロキシによるレスポンスの途切れがないか確認します。
- 短期的なトラブルシューティングの目的でのみ機密ログをオンにします：
  - `SPEC_QC_LOG_SENSITIVE=true`

### 3) LLM に接続できない / リクエストがタイムアウトする

現象：

- 「モデルのリクエスト」段階でスキャンが失敗し、エラーに `request failed` / `ConnectException` / `timeout` が含まれる。

処理メカニズム：

- 1回のリクエストは接続タイムアウトとリクエストタイムアウトの設定によって制御されます（接続の失敗/タイムアウトは例外をスローします）。
- 現在のファイルは「失敗」としてマークされ、エラーメッセージが出力xlsxのエラー行に書き込まれます。
- 詳細なエラースタックは `work/logs/spec-qc.log` に、リクエストイベント/サマリーは `work/logs/large-model.log` に書き込まれます。

トラブルシューティングの提案：

- `llm.base_url` に到達可能かどうかを確認します（企業ネットワーク/プロキシ/イントラネットゲートウェイで特によく見られます）。
- `LLM_API_KEY` が設定されており、有効かどうかを確認します。
- プロキシが必要な場合は、Javaプロセスがそれを使用するように構成されていることを確認します（システムプロキシを介して、またはJavaのhttp/httpsプロキシパラメータを設定するなど）。

### 4) Operation not permitted / 出力を書き込めない

原因：ターゲットの出力ディレクトリが書き込み可能ではありません（macOSのプライバシー権限/サンドボックスディレクトリ/企業ポリシー）。

解決策：

- Web UIで出力ディレクトリを書き込み可能なパスに変更します。
- または、`SPEC_QC_WORK_DIR` を書き込み可能な `work` ディレクトリを指すように設定します。

### 5) .doc ファイルはサポートされていません

現在、`.docx` のみがサポートされています。`.doc` ファイルに遭遇すると、失敗としてマークされ、エラーメッセージが書き込まれます。まず `.docx` に変換してください。
